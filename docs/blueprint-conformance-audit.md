# Blueprint conformance and website security audit

Scope covers the five-page supplied blueprint, current application source, and read-only local MariaDB checks. The PDF is a specification and source of claims to verify. No deployment, provider credential validation, or financial record changes were performed.

| Blueprint requirement | Result | Evidence and limits |
| --- | --- | --- |
| Exact paise math | Core passes | Integer logic in `includes/accounting.php`; 66 unit and database checks passed, including one-paise balances. Some interfaces still cast values to float. This does not establish precision for every legacy screen. |
| Separate security deposits | Core passes; historical data incomplete | Deposit receipts use a separate type and do not settle invoices. Five profiles had deposit targets at the last review, and the local database still has zero deposit receipts. Verified past deposits can be entered from the resident profile. Refund processing is missing. |
| Independent monthly invoices | Pass for new bills | Validator rejects carried dues, duplicate periods and gaps after the latest bill. Five historical invoices retain carried dues and require receipt-level review. |
| FIFO and component order | Core passes | Bulk receipts go to the oldest open invoices, with excess credited to wallet. Allocation order is electricity, rent, maintenance, extra charges and historical dues. A specific-invoice receipt intentionally targets a chosen invoice. |
| Atomic payment approval and wallet updates | Core passes | Payment approval, allocator and ledger transaction helpers use transactions and locks. Temporary-table tests cover rollback. Outbound notifications are separate from accounting. |
| Replay protection | Core passes | Registry keys receipt references and tracks unique external transaction references for applicable payment methods. Tests exercise replay, duplicate external references and historical deposit recording. |
| Protected financial history | Core passes | Eight append-only triggers were verified locally. Wallet edits and deletion of financial history are restricted by application code. A privileged DB account can still alter schema or remove protection. |
| One- and two-month joining payments | Core passes | One month records the deposit and selects arrears. Two months record the deposit and a paid standalone rent invoice and select advance. Zero defers classification. Ten local accounts still have a null billing mode. |
| Meter readings and rent period | Partial | Server checks readings, calculates usage and records separate rent and consumption periods. The UI prefills rent and maintenance from the profile, but the validator accepts the submitted amounts. The blueprint's profile-based price rule is not independently enforced on the server. |
| QR, manual verification and receipts | Implemented in source | Claim submission and admin approval routes exist. Bank settlement is manual. The current review did not perform a real payment, verify the live recipient or rerun a full browser workflow. |
| Three-month outstanding and dashboard totals | Core passes | Shared calculations and regression tests cover multi-month balances, partial payments and independence from stored status flags. Historical carried dues can still affect displayed totals until reconciled. |
| Seven previous bug fixes | Core paths updated | Shared totals address grouped payments and mobile double subtraction. Transaction, exact-money, onboarding invoice and deletion checks address the other five causes. No route-by-route accounting equivalence test was performed. |
| Backup, migration, audit and rollout | Partial | Prior local backup/restore and migration are documented, and local triggers are installed. Migration now requires an explicit target and a backup for non-test targets. Current database tests use localhost port 3306 by default and temporary tables, differing from the PDF's 3308 example. Uploaded-file backup, production restore and live rollout were not verified. |
| Other landlords and properties | Missing | Admins share the existing dataset. Ownership isolation for database records, uploads, QR destinations and reports needs implementation before commercial launch. |
| Legacy billing and reversals | Partial | Legacy creation screens redirect to normal bill generation. The edit validator restricts edits with payment history. Receipt reversals and append-only audit records exist. Formal credit notes, period closing and a deposit refund workflow remain missing. |
| Full accounting statements | Partial | Reports distinguish cash collected, posted deposit and advance receipts, billed amounts and invoice allocations. Full earned-income recognition, unearned-rent and deposit liability statements, journal and bank reconciliation remain missing. |
| Gateway webhooks | Optional and absent | No automatic settlement integration was identified. Manual QR approval remains the workflow. |

## Tokens, keys, and website controls

| Control | Evidence and finding |
| --- | --- |
| Mobile bearer tokens | Seventeen business endpoints call a shared role guard. Login issues a random opaque token and stores only its hash. Tokens expire after 30 days. Logout revokes the token, password changes invalidate it, and inactive residents fail validation. Regression tests passed for invalid, wrong-role and expired tokens. |
| Token transport | The shared API guard ignores query tokens and supports Authorization headers. A POST-body fallback remains for legacy uploads, and some endpoint code still contains redundant legacy parsing after the guard. Installed client versions and historical request logs were not checked. |
| Shareable report tokens | Separate from mobile sessions. Report API uses an expiring random URL token stored directly in the database. It can authorize multiple report endpoints, including renter-related information, without per-report scope. URLs can enter logs and browser history. Share link generation also uses the incoming Host header. Review share scope, token storage, revocation and canonical origin. |
| Receipt signing material | HMAC signing reads its key from the environment or private configuration. Repository history has changes to the signing-key definition. Inspect historical copies privately and plan key versioning and rotation if prior values were committed. Rotation without versioning may affect existing receipt verification. |
| Database and SMTP credentials | Private config files are present locally and are not tracked at their current paths. A filename-only scan identified configuration and mailer references. No provider credential was exercised. Deployment secrets, archived Git objects and the complete environment were not independently scanned or verified. |
| Optional payment provider credentials | The code reviewed uses manual QR approval. No active gateway API key or webhook secret was identified in the relevant application routes. |
| Login and session | Password verification uses password hashes, and web login regenerates the session ID. The shared bootstrap sets HttpOnly, strict mode and SameSite when it runs before session start. Some routes start sessions first. Enforce these options centrally and verify Secure cookies on HTTPS. Login throttling was not established. |
| Request authorization and CSRF | Bill and document deletion now require POST with CSRF verification. Move-out and verified deposit entry also require CSRF. Document proxy compares exact ownership and local Apache previously denied the sampled anonymous private routes. Full authenticated cross-account verification remains outstanding. |
| Upload and error handling | Selected resident uploads use server MIME detection and size limits. Apache has executable extension deny rules. A number of other upload paths remain separate. API exception responses were reduced, but raw database errors remain in some web paths, including `admin/view-renter.php`. |
| SQL safety | Key login and posting statements use prepared queries. Interpolated queries remain; casts, escaping and fixed identifiers need to be assessed individually. This audit makes no blanket claim about injection resistance. |
| Database host | Local connection as root still succeeded without a supplied password. The bind setting is blank, TLS is disabled and binary logging is off. External reachability, firewall restrictions and production settings were not checked. |
| Browser API policy and patching | Several API endpoints allow wildcard CORS. It does not grant bearer access by itself. Production headers, dependency advisories, monitoring, server patch level and backup encryption remain unverified. |

The application substantially implements the single-property rental ledger. Before exposing it to unrelated landlords, isolate property data. For the current deployment, prioritize the local database account and networking, server-side pricing, report share tokens, session settings, and reconciliation of the historical accounts.
